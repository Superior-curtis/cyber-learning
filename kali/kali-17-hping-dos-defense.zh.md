# hping 與 DoS/DDoS：指令、邏輯與藍隊防禦

> 📅 2026-08-05 · 深入研究
> hping3 是封包製作工具，也是測試 DoS 韌性的經典方式。這篇講透 flood 的邏輯、給出「只限 homelab」的壓力測試指令，並把藍隊的偵測與緩解講到一樣透。

---

DoS/DDoS 是「可用性攻擊」——目的不是偷資料，而是**讓服務癱瘓**。`hping3` 是 Kali 裡做這類「韌性測試」的經典工具。這篇講透背後的邏輯，給出**只限 homelab** 的測試指令，並把藍隊防禦放到同等的份量。

> 安全說明（HOMELAB ONLY）：本頁所有指令只允許對你自己的 homelab 伺服器、在隔離環境執行。對任何真實目標發動 DoS/DDoS 都是犯罪且極具破壞性，在多數司法管轄區會面臨嚴重的刑事責任。這是一堂防禦課。

## DoS/DDoS 是什麼

* **DoS（Denial of Service）**：單一來源，讓目標服務無法使用。
* **DDoS（Distributed DoS）**：大量來源同時發動，更難抵擋。

它是 `found-02-cia` 的「可用性（Availability）」被打掉：服務還在，但**合法使用者進不來**。

## 為什麼有效：資源耗盡的邏輯

任何服務的資源都是有限的——連線狀態表、頻寬、CPU。**flood 的邏輯就是：送超過它能處理的量，讓它在處理垃圾時，沒力氣服務真人。**

兩條主攻線：

* **耗盡狀態**：佔滿伺服器的「連線狀態表」，讓新的合法連線進不來。
* **耗盡頻寬**：灌爆網路頻寬，讓所有流量塞在路上。

## 常見手法

| 手法 | 耗盡什麼 | 一句話 |
|---|---|---|
| SYN flood | 連線狀態表 | 大量半開連線佔滿表 |
| UDP flood | 頻寬/處理 | 大量 UDP 封包灌爆 |
| ICMP flood | 頻寬 | 大量 ping |
| Slowloris | 連線數 | 慢慢開一堆連線掛著 |
| 放大攻擊 | 頻寬 | 用反射放大（DNS/NTP） |

## SYN flood 的邏輯（TCP 握手）

SYN flood 是最經典的一種，邏輯建立在 `net-01-network-fundamentals` 的 TCP 三步握手上：

1. 客戶端送 `SYN`，伺服器回 `SYN-ACK`，並**保留一條「半開連線」**等最後的 `ACK`。
2. flood = 送大量 `SYN` 卻**永不完成握手** → 半開連線一條條堆積。
3. 連線狀態表滿了 → 真使用者連 `SYN` 都排不進來。

**關鍵：伺服器「信了每個 SYN 都會完成」，這就是它被耗盡的原因。** 緩解的邏輯也因此很明確——見「藍隊防禦」。

## hping3：封包製作工具

`hping3` 能打造並送出**任意內容的封包**——這讓它在合法用途上是強大的網路測試工具（測防火牆、測 TCP 堆疊），在錯誤手上則能製造 flood。安裝很簡單：

```bash
# 安裝
sudo apt install hping3
```

> hping3 的力量來自「可自訂 + 可大量」：它讓你把一個封包的每個欄位都調成你要的，然後（在授權場合）重複送出。理解「可自訂」與「可大量」這兩件事，你就理解 flood 與它的緩解各打在誰身上。

## homelab 壓力測試指令（只限自己的伺服器）

先從**最無害**的開始：對自己的本機送**一個**測試封包，觀察回應。

```bash
# 對自己的本機送一個 SYN 封包，觀察 TCP 回應（無害）
hping3 -S -p 80 127.0.0.1
```

要驗證**你自己伺服器**對 SYN flood 的韌性，只能在隔離的 homelab 網路、對**你自己的**伺服器 IP：

```bash
# HOMELAB ONLY — 只對你自己的伺服器 IP，且只在一台獨立的測試機
hping3 -S --flood -p 80 192.168.1.10
```

> 安全說明（再次強調）：--flood 會極快送出大量封包。只限你自己的 homelab 伺服器、只在隔離網段。對任何不是你的目標執行這條指令，就是發起 DoS 攻擊——違法且可能讓你吃上官司。測完立刻觀察自己的日誌與連接表，驗證緩解是否生效。

## 藍隊防禦

防禦分「偵測」與「緩解」兩層：

**偵測（`blue-02-logging-siem` 的基線思路）：**

```bash
# 看半開連線（SYN-RECV）數量——暴增就是 SYN flood 的徵兆
ss -tan state syn-recv | wc -l

# 用 tcpdump 抓「只有 SYN、沒有 ACK」的封包
tcpdump -i eth0 "tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0"
```

**緩解：**

| 措施 | 做法 |
|---|---|
| SYN cookies | 不佔狀態表，直接算回應（`net-02-tls-https` 對應層級） |
| 速率限制 | 限制單一來源的連線建立速率 |
| 防火牆 | 攔截異常來源與協定（`net-04-firewalls-vpn-proxy`） |
| CDN / DDoS 防護 | 大流量時引流清洗，分散壓力 |
| 冗餘架構 | 多節點分散，單點被打不至於全滅 |

> 防禦心法：攻擊在「資源與速率」上施壓，防禦就在「資源與速率」上設限。 先有基線（blue-02-logging-siem）才知道「異常」長什麼樣；再有緩解，才有能力在異常出現時扛住。

## 安全說明

* ✅ 可以：在**你自己的 homelab**，對**你自己的伺服器**做韌性測試，觀察與驗證防禦。
* ❌ 不可以：對任何真實或第三方的目標發動 DoS/DDoS——不管動機多「純」。
* ⚠️ 記住：DoS 是破壞性攻擊；未經授權發動，在多數地方是嚴重的刑事犯罪（`career-03-ethics-law`）。

#### Q: SYN flood 能癱瘓伺服器的關鍵原因是什麼？

* 伺服器算力太弱

* 伺服器信任每個 SYN 都會完成握手，因而保留大量半開連線，直到狀態表被佔滿

* 伺服器沒有防火牆

* SYN 封包太大

> 💡 伺服器為每個 SYN 保留半開連線狀態等待 ACK；flood 送大量 SYN 卻不完成握手，狀態表滿了就再也進不來合法連線。
