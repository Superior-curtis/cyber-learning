# 使用者、群組與 sudo

> 📅 2026-08-05 · 使用教學
> 在 Linux 裡，每件事都必須以某個身分執行。看懂使用者、群組與 sudo，你就同時看懂了權限、攻擊面與最小權限原則。

---

剛開始碰 Linux 的人，最常問的一句誠實的話是：「root 什麼都能做，那我直接用 root 就好啦，幹嘛搞那麼複雜？」這個直覺完全合理——root 確實萬能。但「萬能」正是它危險的原因。這篇文章要把三件事講清楚，它們是安全使用 Linux 的地基：**使用者（users）、群組（groups）與 sudo**。

Linux 天生就是多人作業系統。你在 `linux-03-permissions` 學到的 rwx 權限，全部建立在「你以誰的身分執行」這個前提上。先懂身分，再談權限，你對整個系統的理解會突然通順起來。

## 每件事都有一個「身分」

Linux 的鐵律：**沒有任何東西可以脫離身分而存在。** 每個程序、每個檔案、每個執行中的動作，都一定屬於某個使用者。你打開終端機的那一刻，背後的 shell 就帶著作業系統裡某個帳號的身分在跑。

這就是為什麼「我以誰的身分操作」如此關鍵。系統不會問「這個動作合不合理」，它只會查「這個身分有沒有權限」。權限對了就放行，錯了就拒絕——**身分決定了一切規則的起點。**

你可以親眼看一看：

```bash
whoami        # 現在的我，是作業系統裡的誰
id            # 我的 UID、主要群組，以及其它群組
```

## 用與不用：/etc/passwd 與 /etc/shadow

那這些身分住在哪裡？兩個檔案。一個每個人都能讀，一個只有 root 能讀：

| 檔案 | 存什麼 | 誰能讀 |
|---|---|---|
| `/etc/passwd` | 使用者名稱、UID、家目錄、預設 shell | 所有人 |
| `/etc/shadow` | 密碼雜湊、密碼期限與鎖定狀態 | 只有 root |

把密碼雜湊從 passwd 搬到 shadow，是 Linux 歷史上一大步。早期密碼雜湊直接寫在 passwd 裡，任何能讀檔案的人都能拿去離線破解。現在雜湊鎖在 shadow 裡，而且只有 root 能碰——這正是你在 `pass-01-how-passwords-are-stored` 學到的「雜湊要藏好」在系統層面的落實。

> 自己看一下。`cat /etc/passwd`，每一行是一個帳號，欄位用冒號分隔。你會看到一堆不像人的帳號——那些是系統程序在用的，見下一節。

實際打開一行，它是長這樣的：

```bash
alice:x:1000:1000:Alice,,,:/home/alice:/bin/bash
```

逐欄拆開（用冒號分）：使用者名稱、密碼欄位、UID、主要群組的 GID、註解、家目錄、預設 shell。注意密碼欄位只有一個 `x`——真正的雜湊在 shadow。這不是省略，而是刻意的系統設計：**即使 passwd 每個人都能讀，裡面也不含任何可以被破解的密碼材料。**

## UID：數字才是真正的身分

使用者名稱只是給人看的標籤。系統真正認的是 **UID**。同一個數字，改個名字，權限完全不受影響。

| UID 範圍 | 用途 | 例子 |
|---|---|---|
| `0` | root，最高權限 | root |
| `1–999` | 系統帳號，給服務與守護程序用 | www-data、sshd |
| `1000+` | 一般使用者帳號 | 你自己 |

那些「不像人的帳號」就是系統帳號：`www-data` 跑網頁伺服器、`sshd` 跑 SSH。**每個服務都用一個自己的帳號**——就算某個服務被入侵，破壞範圍也被限制在它的帳號權限內。這是「最小權限原則」在系統層級的實作，同一句話，在 `found-04-threat-modeling` 之後你已經看過好幾次了。

## 群組：把權限交給「一群人」

如果每次都要針對單一使用者給權限，管理會瘋掉。所以 Linux 有**群組（group）**：一個群組是一組使用者的集合，權限可以發給整個群組，而不是一個人一個人發。

還記得 `linux-03-permissions` 的 rwx 嗎？每一組權限都分成三格：**擁有者、群組、其他**。檔案擁有者預設在自己主要群組裡，額外還能加入其它群組，來取得更多檔案的存取權。

| 角色 | 身分 | 權限範圍 |
|---|---|---|
| 擁有者（user） | 檔案的主人 | 只影響一個人 |
| 群組（group） | 一群使用者 | 影響一組人 |
| 其他（other） | 任何人 | 全部人 |

群組的威力在於**共用**：一群開發者加進 `developers` 群組，就能一起讀專案資料夾；`sudo` 群組的成員可以使用 sudo——這個群組特別重要，稍後會講。

## root 的誘惑與代價

現在回到開頭的問題：為什麼不要永遠用 root？因為 root 身上同時背著兩件事：**不受限制的力量**，與**不受限制的破壞力**。

| root 很爽的地方 | root 很痛的地方 |
|---|---|
| 什麼都能裝 | 一個字打錯，整台機器再見 |
| 不用管權限 | 權限檢查形同虛設 |
| 沒有「被拒絕」這件事 | 惡意程式也跟著你「沒有被拒絕」 |

最後一行是關鍵。**你以 root 執行時，系統裡每一段惡意程式碼也以 root 執行。** 你可能只是不小心中了一招藏在檔案裡的指令，而它的權限和你一樣大。用 root 不是讓自己更方便，是讓系統裡「任何一個意外」都變成「全系統災難」。

> 只用普通帳號做日常事。 永遠不要用 root 登入做例行工作；root 密碼等於系統的全部鑰匙——不分出去、不輸進網頁、不寫在筆記軟體裡。如果你在授權的測試環境或 CTF 實驗室練習權限操作，也請一律先建立一個普通帳號，再透過 sudo 提升權限。

## 最小權限原則

把上面的一切收斂成一句話，就是資安界最常引用的原則：**最小權限原則（Principle of Least Privilege）**——任何身分都只給「完成工作所必需」的最少權限，不多給一分。

* 使用者只做日常該做的事，別預設給管理員權限。
* 每個服務用自己的系統帳號，不共用 root。
* 檔案權限能鎖就鎖，群組夠用就好，不要開給「所有其他人」。

這個原則不是為了刁難人，而是讓**破壞半徑**變小。你無法保證系統百分之百不出錯；但你完全可以保證「就算出錯，影響範圍很小」。

## sudo：把權限「借」來用

那真的需要管理操作時怎麼辦？答案是 **sudo**——用普通帳號登入，臨時以 root 身分執行「單一」指令：

```bash
sudo apt update
```

關鍵字是「單一」。你用普通帳號的身分活著，只有在需要時，才把管理權限借來一下，用完立刻還回去。這帶來三個好處：

* **要執行就必須明確說「我要」**，減少無意識的破壞。
* **留下紀錄**：誰、在什麼時候、執行了什麼管理指令，都寫進日誌。
* **不用分享 root 密碼**：多個管理員各自用自己密碼，出事知道找誰。

誰能用 sudo？看 `/etc/sudoers` 檔，或使用者是否在 `sudo` 群組裡。這是一個**很重要的審查對象**——每次交接、每個離職的工程師，都該重新檢查一遍。少一個人能用 sudo，就少一分「帳號被濫用」的風險。

## 帳號的生命週期

帳號也有出生、活著與死亡。資安角度最常出問題的，反而是「死亡」這一段：

| 階段 | 動作 | 資安要點 |
|---|---|---|
| 建立 | `useradd` 新增帳號 | 一開頭就給最小權限 |
| 使用 | 日常登入、sudo | 密碼要強、能開 MFA 就開 |
| 停用 | 離職、不再使用 | 先鎖定帳號，不要只改密碼 |
| 刪除 | 確認不再需要 | 連同群組、家目錄一起清點 |

最常見的漏洞不是「多了一個帳號」，而是「離職的人帳號還活著」。攻擊者拿到一個舊帳號，等於拿到一扇沒換鎖的門。這個「生命週期」的想法，在 `blue-07-iam-zero-trust` 會擴展成整個企業的身份管理。

## 資安該怎麼看使用者

把這一章變成一份「檢查清單」的形狀：

| 檢查 | 你在找什麼 |
|---|---|
| `cat /etc/passwd` | 有沒有不認識的新帳號 |
| `getent group sudo` | 誰有 sudo 權限——是不是都該有 |
| 帳號盤點 | 沒在用的帳號是不是還活著、還沒刪 |

攻擊者很常做的第一件事，就是**想辦法弄出一個自己的帳號**，或把已有帳號加進 sudo 群組。定期看這幾行，是免費又有效的偵測。這些檔案與權限，會在你往後每一次加固（`linux-09-hardening-basics`）中反覆出現。

#### Q: 為什麼資安建議「日常作業用普通帳號，需要時才用 sudo」，而不是直接以 root 登入？

* root 登入速度比較慢，普通帳號比較快

* 以 root 執行時，任何惡意程式碼也會獲得 root 的權限，讓一次小意外變成全系統災難

* root 帳號不能安裝任何軟體，所以只能用普通帳號

* 普通帳號的權限比 root 更高，更適合日常使用

> 💡 這正是最小權限原則：日常用最小權限，必要時才提升。以 root 執行時，所有程式（包括惡意的）都擁有最高權限，破壞半徑因此無限放大。
