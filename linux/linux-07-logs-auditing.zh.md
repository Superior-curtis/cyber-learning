# 日誌與稽核（/var/log、journalctl）

> 📅 2026-08-05 · 深入研究

---

## 系統的記憶，寫在每個檔案裡

電腦不會聊天，但它非常會寫日記。幾乎每一件發生在你 Linux 系統上的事——誰登入了、哪個服務掛了、網路卡何時斷線、誰用 root 執行了什麼——都會被記錄在某個地方。這些記錄，就是**日誌（logs）**。

對藍隊來說，日誌的地位就像是案發現場的監視器：不是每一捲帶子都有案情，但真正出事的那一天，你需要的不是推測，而是那段錄影。這一章我們把「錄影帶放在哪、怎麼播放、出事先看哪一段」一次講清楚。

## 兩大日誌體系：syslog 與 journald

Linux 日誌世界裡有兩個「接線生」，負責把各處來的訊息分類寫下。搞清楚這兩位，等於拿到日誌地圖。

| 體系 | 檔案位置 | 特性 |
|------|---------|------|
| **syslog（rsyslog）** | `/var/log/*.log` | 純文字檔，老牌、可被各種工具直接 `grep`，可設定格式與轉送 |
| **journald** | 二進位資料庫（`/var/log/journal/`） | systemd 內建，自動收錄所有服務輸出，支援結構化欄位與即時查詢 |

`systools` 時代就存在的 syslog 是「文字派」，每一行都是人類可讀的日誌；journald 是 systemd 的「資料庫派」，除了文字還夾帶時間、PID、來源等結構化欄位。兩者常常同時運行，而且是**同一份故事的兩種記法**——journald 可以把手上的訊息轉交給 syslog，syslog 再寫成傳統檔案。

**看的順序**：`journalctl` 先看整體（尤其服務輸出），`/var/log` 的檔案再看系統層事件。兩者互相補充，缺一不可。

## /var/log：系統日誌的抽屜櫃

`/var/log` 是傳統文字日誌的家。最值得認識的幾個「抽屜」：

| 檔案 | 記的是什麼 | 對藍隊的意義 |
|------|-----------|-------------|
| `/var/log/auth.log` | 登入與身分驗證（SSH、sudo、su） | 誰在試圖登入你的機器，第一優先 |
| `/var/log/syslog` | 系統與應用程式的綜合訊息 | 出錯時的總覽 |
| `/var/log/dmesg` | 核心開機訊息與硬體事件 | 硬體層異常、開機錯誤 |
| `/var/log/kern.log` | 核心本身的日誌 | 核心級異常 |
| `/var/log/apt/history.log` | 套件安裝與移除 | 誰在何時裝了什麼 |

`auth.log` 是藍隊最重要的單一檔案。成功與失敗的 SSH 登入、`sudo` 執行、`su` 切換，全都寫在這裡。查看最近的登入嘗試：

```bash
# 看最近的登入與認證事件
tail -n 50 /var/log/auth.log

# 只留下「失敗」的登入嘗試
grep -i "failed password" /var/log/auth.log | tail -n 20

# 看誰用過 sudo
grep "sudo:" /var/log/auth.log | tail -n 20
```

## journalctl：把整個系統握在手心

systemd 系的發行版（Ubuntu、Debian、Fedora、Arch 都算）用 `journalctl` 查 journald 收集的日誌。它不需要開一堆檔案，直接在一個地方搜全部服務：

```bash
# 最新 50 筆，跟著新增內容（類似 tail -f）
journalctl -n 50 -f

# 只看某個服務（例如 SSH）
journalctl -u ssh

# 看某個時間點之後發生的事
journalctl --since "2 hours ago"

# 只列出 SSH 的登入成功事件
journalctl -u ssh | grep "Accepted"
```

> 日誌先設「保留多久」再談別的。 journald 預設會吃掉一定的磁碟空間，設好保留上限，你才不會在需要調閱三個月前紀錄時，發現早就被清掉了。系統管理員的職責，是讓「記憶」這件事本身可靠。

## dmesg：開機那一刻的真相

系統開機時，核心從硬體自檢到掛載磁碟，每一步都寫進**核心環形緩衝區**，而 `dmesg` 就是把這條緩衝區讀出來給你看的工具。它通常記錄在 `/var/log/dmesg`。

什麼時候需要它？伺服器無預警重開、外接碟消失、網路卡不認得——這些「硬體層」的謎題，日誌都在 dmesg 裡。現代版本的 `journalctl -k` 也能看到同樣內容：

```bash
# 直接看核心訊息
dmesg | tail -n 30

# 用 journalctl 看核心日誌（等價）
journalctl -k -n 30
```

## 日誌輪替：讓日誌活得比你想像久

日誌如果不控制大小，總有一天填滿磁碟、拖垮系統。**日誌輪替（log rotation）**就是答案：當某個日誌到達設定的大小或時間，系統把它改檔名封存，並開一個新的繼續寫，只保留最近 N 份。

設定住在 `/etc/logrotate.d/`，例如：

```bash
# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
  weekly
  rotate 4
  compress
  missingok
}
```

意思是：每週輪替一次、保留 4 份、舊檔壓縮。**封存下來的舊日誌是稽核的寶藏**——攻擊者常在事發後才被發現，若你在輪替前就把舊檔刪了，等於自毀證據。設定輪替時，保留期至少要涵蓋你的合規與稽核需求。

## 出事之後：藍隊的「先看哪裡」清單

日誌不是拿來每天讀的，而是「出事那一刻」查的。事件發生後，依序看這幾處：

1. **`/var/log/auth.log`** ——有沒有人從陌生 IP 成功登入？有沒有密集的失敗嘗試？「誰進來過」是第一個問題。
2. **`journalctl --since`** ——從你懷疑的時間點開始，所有服務發生過什麼。
3. **`last` 與 `lastb`** ——最近的登入紀錄（`lastb` 顯示失敗的），秒查登入歷史。
4. **`history` 與 shell 歷史** ——使用者帳號內執行過什麼指令（前提是歷史有開啟）。
5. **排程任務** ——檢查 `crontab -l` 與 `/etc/cron*`，攻擊者常駐技術之一就是在這裡塞持久化指令。

> 這一章的查法，全部是管理自己機器的正常操作。未經授權檢視別人的系統或日誌，本身就可能違法——日誌工具是防禦者的手電筒，不是闖空門的工具。

## auditd：內建的事件稽核框架

`/var/log` 記的是「系統自己說的話」；但有時候你要稽核的是「某個檔案被誰動過、某個指令被誰執行」——這就需要 **auditd**，Linux 內建的事件稽核框架。它監聽核心層事件，把檔案開啟、程式執行、權限變更等動作記成稽核紀錄，回答的是「誰在何時動了什麼」這個等級的問題。

```bash
# 安裝並啟用
sudo apt install auditd
sudo systemctl enable --now auditd

# 監視敏感檔案（以 /etc/shadow 為例，-p wa = 寫入與屬性變更）
sudo auditctl -w /etc/shadow -p wa -k shadow_watch

# 查詢稽核紀錄中有關 shadow 的存取
sudo ausearch -k shadow_watch
```

auditd 對藍隊的價值在於：即使事發當下沒人盯著日誌，稽核紀錄也會留下「哪個程序、哪個使用者、幾點幾分的存取」完整軌跡。配合 `linux-05-processes-services` 的觀念，你可以把監視從服務層延伸到檔案層——這正是「稽核」兩個字的精髓。

## 把日誌變成真正的防禦

單機的日誌，威力有限；真正的大局，是把所有機器的日誌集中到一個地方統一搜尋與告警——這就是 **SIEM**（資安資訊與事件管理）要做的事。當你已經會看單機日誌，把同樣的語法搬到 SIEM 上，你就能回答「整個機房今天有沒有人被暴力破解」這種問題。下一步，`blue-02-logging-siem` 會帶你把日誌從「單機抽屜」升級成「全公司的監視網」。

#### Q: 事件發生後，藍隊最優先查詢的第一個問題是什麼？

* 誰在何時成功登入過這台機器

* 系統開機花了幾秒鐘

* 核心版本是不是最新的

* 磁碟剩餘空間有多少

> 💡 誰進來過、誰試過但失敗了，是事件應變的第一個問題；答案通常在 /var/log/auth.log 與 last 指令裡。開機時間、核心版本、磁碟空間都是日常維運問題，不是事件查詢的起點。
