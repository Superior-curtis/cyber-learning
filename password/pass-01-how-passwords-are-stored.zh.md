# 密碼如何被儲存（hash / salt / pepper）

> 📅 2026-08-05 · 核心概念
> 網站不會存你的密碼原文，而是存它的指紋。了解 hash、salt、pepper 如何把密碼變成難以還原的雜湊值，以及為什麼這套設計在資料庫外洩時能保護你。

---

想像你是一家咖啡店的店員，把每位客人的信用卡號寫在牆上的白板上。任何走進店裡的人，只要拍張照，就能偷走所有卡號。很不幸，很多早期網站就是這樣存密碼的：直接存明文。直到資料庫外洩成為常態，大家才學到教訓——**密碼不該被「儲存」，而是該被「轉化」。**

這一篇要解釋現代網站真正存的是什麼，以及那套 hash / salt / pepper 的設計，如何在最壞情況（資料庫整包被偷走）下仍然保護你。如果你還沒讀過 `crypto-01-hash-vs-encryption` 與 `crypto-02-password-hashing`，建議先看——那兩篇把 hash 的基本性質講得很清楚。

## 三種存法，三種災難等級

先看歷史上的三種做法，你就知道這題為什麼重要：

| 存法 | 白話 | 資料庫被偷後 |
|---|---|---|
| 明文（plaintext） | 直接存密碼原文 | 全部密碼直接裸露，災難 |
| 加密（encryption） | 用金鑰加密，可解密還原 | 金鑰若一起被偷，等於明文；金鑰本身還要找地方藏 |
| 雜湊（hashing） | 單向轉換成固定長度指紋 | 無法直接還原，但仍有弱點可被破解 |

關鍵差別在於**方向性**。加密是雙向的：有金鑰就能還原，所以金鑰保管變成另一個保險庫。hash 是單向的：轉過去就回不來，這正是密碼需要的——**系統根本不該有能力「還原」你的密碼。**

## Hash：密碼的指紋

Hash（雜湊）演算法把任意長度的輸入，變成固定長度的字串。同一個輸入永遠得到同一個輸出，但只要輸入改一個字，輸出就完全不同。

以 `sha256` 為例（教學示範用，實際存密碼有更好的選擇）：

```bash
# 把密碼轉成 hash（只是概念示範）
echo -n "correct horse" | sha256sum
# 6d2582b8...（固定 64 個十六進位字元）
```

這個 hash 就是「指紋」：網站只驗證指紋，不驗證原文。你輸入密碼，網站把它 hash 一遍，比對與資料庫裡存的 hash 是否相同。因為雜湊是單向的，攻擊者拿到資料庫，也無法直接知道你的密碼。

但這裡有個致命問題。人類密碼其實不多：`password`、`123456`、`iloveyou`……攻擊者可以先把常見密碼全部 hash 一遍，建立一張「查表」，再拿偷來的資料庫比對。這種表叫**彩虹表（rainbow table）**。同樣的密碼、同樣的 hash 演算法，就會產生同樣的 hash——查表一擊即中。

## Salt：讓每個人都長得不一樣

解決彩虹表的辦法，就是在 hash 之前先加入一段隨機的「鹽」（salt）。

* 每個使用者產生**不同的隨機 salt**。
* 儲存的不是 `hash(密碼)`，而是 `hash(密碼 + salt)`，同時把 salt 一起存下來。
* 因為 salt 人人不同，就算是同樣的密碼，hash 出來也不同——彩虹表瞬間失效。

| | 沒加 salt | 加了 salt |
|---|---|---|
| 相同密碼 | 產生相同 hash，可查表比對 | 產生不同 hash，查表失效 |
| 預先算好的表 | 對所有使用者有效 | 每個使用者都要重算 |
| 成本 | 攻擊者算一次，打全部 | 攻擊者算一次，只打一人 |

salt 不需要保密。它的目的不是「藏起來」，而是「讓每個人的 hash 都獨一無二」。就算 salt 公開，攻擊者依然被迫對每個使用者分別破解。

## Pepper：伺服器端的最後一道鎖

Salt 存在資料庫裡，pepper（胡椒）則不同：它是**一個伺服器端才有的祕密值**，不跟 hash 一起存。

* 儲存的是 `hash(密碼 + salt + pepper)`。
* pepper 在資料庫外洩時**不會一起外洩**，攻擊者只拿到 hash 與 salt，缺了 pepper 這個關鍵原料。
* 即使資料庫整包被偷，攻擊者還缺一段資訊，破解成本大幅上升。

| | Salt | Pepper |
|---|---|---|
| 存哪 | 與 hash 一起存資料庫 | 存在伺服器端，獨立於資料庫 |
| 保密 | 不需要保密 | 必須保密 |
| 外洩後 | 攻擊者照樣能逐一破解 | 攻擊者缺原料，破解受阻 |
| 每位使用者不同？ | 是，人人不同 | 否，通常是整個系統共用一個 |

> 把三層想成一整串：hash 讓密碼無法還原，salt 讓每個人的結果獨一無二，pepper 讓資料庫外洩時攻擊者仍缺關鍵原料。 三者合起來，就是現代密碼儲存的標準姿勢。

## 登入那一刻：完整流程

把前面幾節串起來，看一次「登入」到底發生什麼：

#### 使用者輸入密碼

密碼只在使用者與網站之間傳輸，而且應該走 HTTPS（見 found-05-how-the-web-works）。

#### 網站取出該使用者的 salt

每個使用者有自己的隨機 salt，存在資料庫裡。

#### 網站計算 hash(密碼 + salt + pepper)

用 bcrypt 這類慢演算法計算，把結果與資料庫裡存的 hash 比對。

#### 相同就登入成功

網站只比對「指紋」，從頭到尾沒有看過、也不需要還原密碼原文。

注意最後一步的意義：**整個系統裡，根本沒有地方存著「你的密碼」可以被打開。** 這就是「轉化」與「儲存」的差別。

## 用對演算法，而不是自己造

就算加了 salt，`sha256` 這種「快速」的 hash 也不適合存密碼，因為太快了——攻擊者每秒可以試幾十億次。專門設計給密碼的演算法，故意**很慢**：

| 演算法 | 特色 | 用途 |
|---|---|---|
| bcrypt | 內建 salt，可調整成本 | 最常見的密碼 hash |
| scrypt | 吃記憶體，抗硬體加速 | 記憶體密集，更難暴力破解 |
| argon2 | 現代標準，可調記憶體與時間 | 目前的首選之一 |

> 任何「自行設計」的密碼保護方案都是危險訊號。用 bcrypt、scrypt 或 argon2 這類經得起檢驗的標準演算法，讓正確的工程師已經替你踩過坑。安全靠的是成熟的設計，不是祕密發明。

慢，正是防禦的重點：密碼 hash 的目標不是「快」，而是讓**每一次嘗試都貴得讓攻擊者放棄**。`pass-02-cracking-101` 會從攻擊者的角度，展示這些演算法到底怎麼被嘗試破解——那是理解防禦的另一半。

## 常見錯誤，一一對照

把最常見的錯誤與對策排成一張表，開發時照著檢查：

| 常見錯誤 | 為什麼危險 | 正確做法 |
|---|---|---|
| 用 MD5 或 SHA-1 | 太快，且有已知碰撞 | 改用 bcrypt / scrypt / argon2 |
| 不加 salt | 彩虹表一擊即中 | 每次註冊都產生新的隨機 salt |
| 用快速 hash 當密碼 hash | 每秒可試幾十億次 | 用故意很慢的演算法 |
| 自製「加密變形」 | 沒有專業檢驗，極易出錯 | 用標準演算法，別自己發明 |
| 把 pepper 跟 hash 放一起 | 外洩時一起被偷 | pepper 獨立存放於伺服器 |

幾乎每一樁「密碼外洩」的悲劇，都可以在上表找到至少一格。防禦的重點不是追求完美，而是把這幾格都填對。

## 資料庫外洩的現實：儲存設計就是全部

把「攻擊者會拿到 hash 檔案」當成前提，而不是假設。回顧那些重大外洩事件：駭客帶走的通常是整包資料庫，包括 hash 與 salt。真正決定使用者安不安全的分水嶺，就是儲存設計本身。

這也解釋了為什麼一直有「密碼外洩」的新聞，卻很少看到對應的帳號真的被登入——好的儲存設計，把一次外洩從「全部淪陷」變成「逐個硬碰硬」。`pass-05-real-breaches` 會帶你看真實案例中，設計好壞如何決定災難規模。

## 對使用者，也對開發者

如果你是使用者，這篇教你一件事：**在同一個網站重複用密碼，等於把雞蛋放進同一個籃子。** 無論網站怎麼保護，你還是該用獨特的密碼與密碼管理器。`pass-04-defenses` 之後會談到防禦的完整拼圖。

如果你是開發者，這篇就是你的待辦清單：

1. 絕不存明文。
2. 用 bcrypt / scrypt / argon2，而不是自製演算法。
3. 依賴演算法內建 salt，或自行加上隨機 salt。
4. 有條件的話加上 pepper，分離儲存。
5. 把「資料庫會外洩」當成必然，設計時就為它準備。

#### Q: 為什麼現代網站用 hash 而不是加密來儲存密碼？

* hash 比較快，使用者登入不用等

* hash 是單向的，系統本身無法還原密碼，外洩時風險更低

* 加密需要金鑰，而金鑰太貴買不起

* hash 可以把長密碼變成比較短的密碼

> 💡 加密是雙向的：有金鑰就能還原，代表系統有能力還原密碼，也代表金鑰外洩等於明文外洩。hash 是單向的，系統只驗證指紋、無法還原原文，這正是密碼儲存需要的性質。
