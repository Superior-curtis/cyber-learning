---

## 密碼外洩不是運氣差，而是設計差

過去二十年，網路世界發生過好幾次「百萬級」密碼外洩。有人覺得這是駭客武功高強，但把案件攤開來看，真正讓數億帳號「裸奔」的，往往是同一件事：**公司把密碼放錯了地方**。

這篇文章把四起最常被提起的案例當成教材，逐個拆解——**當時出了什麼事、根因在哪、防禦上我們該學到什麼**。每一課都不需要頂尖駭客技巧才能理解，卻需要每個工程師（包括你）牢牢記住。

> 這篇文章是防禦教材，不是攻擊手冊。請不要拿外洩的密碼資料做任何未經授權的事——未經授權存取他人的帳號與資料，在臺灣與多數國家都是違法行為。

## 案例一：RockYou（2009）——明文儲存的代價

RockYou 是一家做 Facebook 小遊戲的公司。2009 年，攻擊者用 SQL 注入攻入它的資料庫，帶走約 3,200 萬筆使用者密碼。最震撼的是：**這些密碼全部以明文（plaintext）儲存**。攻擊者不需要破解任何東西，直接把整個表格複製回家就行。

### 哪裡出了問題？

* 密碼直接寫在資料庫裡，等於把大門鑰匙貼在門框上。
* 沒有任何雜湊、加密或遮蔽，連「加一層」都沒有。
* 事件本身（SQL 注入）是入口，但傷害的規模，完全是密碼存放方式決定的。

### 防禦教訓

1. **密碼永不存明文**。無論如何，使用者的密碼都不該以可讀形式出現在任何儲存空間。
2. 用**慢速、加鹽**的雜湊演算法（如 bcrypt、argon2、scrypt）存放。
3. 就算被入侵，也要讓攻擊者在「拿到資料」與「能用資料」之間，隔一道牆。

> 複習一下雜湊與加密的差別：可以回去看 `crypto-01-hash-vs-encryption` 與 `crypto-02-password-hashing`。

## 案例二：LinkedIn（2012）——鹽不是可選項

2012 年，LinkedIn 遭遇入侵，最初流出 650 萬筆密碼的 SHA-1 雜湊；2016 年，更完整的約 1.17 億筆帳號資料在網路上被兜售。

LinkedIn 不是存明文——它用了 SHA-1。問題是這個 SHA-1 **沒有加鹽**。

### 為什麼「沒加鹽」是致命的？

* SHA-1 非常快：用 GPU 可以每秒算數十億次，暴力破解成本極低。
* 沒有鹽，代表**相同密碼會得到相同的雜湊**。兩個使用者都設同一個密碼，就會得到一模一樣的雜湊——攻擊者算一次，等於破解兩人。
* 沒鹽的雜湊還可以比對「彩虹表」（預先算好的密碼→雜湊對照表），幾秒鐘就查出常見密碼。

### 防禦教訓

1. 用 **bcrypt / argon2 / scrypt** 這類刻意「慢」的自適應演算法，把暴力破解的成本拉高到不划算。
2. **每個密碼都要有獨一無二的鹽**，讓相同的密碼產生不同的雜湊。
3. 密碼強度之外，雜湊演算法的選擇，直接決定外洩之後有多少密碼會被還原。

## 案例三：Adobe（2013）——加密不是雜湊

2013 年，Adobe 遭入侵，超過 1.5 億筆使用者記錄外洩，其中包括密碼與密碼提示問題的答案。Adobe 用了 3DES 加密來保護密碼，還把所有密碼**共用同一把金鑰**。

### 哪裡出了問題？

* **加密是可逆的**。只要有金鑰（或能猜出金鑰），就能把密碼解回明文。Adobe 的金鑰就藏在被一起帶走的資料裡。
* 密碼**提示問題**（如「你的寵物叫什麼？」）讓破解變得更簡單——提示本身常常就是答案的一部分。
* Adobe 內部自己也在重用密碼，導致入侵在系統之間橫向擴散。

### 防禦教訓

1. **雜湊 ≠ 加密**。雜湊是單向的，加密是可逆的；密碼驗證要用單向雜湊，而不是可逆加密。
2. **金鑰管理**要和密碼分開存放，而且要獨立、定期輪換。
3. 移除「密碼提示」，或至少不讓它洩漏太多資訊。
4. 內部系統也不要重用密碼——同一組憑證不該同時保護開發、測試與生產環境。

## 案例四：23andMe（2023）——密碼重用的連鎖效應

2023 年，基因檢測公司 23andMe 遭入侵，約 690 萬筆族譜資料被爬取。攻擊方式不是高超的漏洞利用，而是**憑證填充（credential stuffing）**：拿先前外洩的「舊帳號＋舊密碼」組合，去嘗試登入其他網站。只要使用者重用密碼，這招就有效。

### 為什麼特別值得警惕？

* 攻擊者手上早就有一堆外洩組合，**不需要破解任何新東西**。
* 23andMe 的「DNA 親屬」功能是預設開啟分享的，攻擊者爬進一個帳號，就能連帶看到親屬的資料。
* 這告訴我們：你的密碼可能從來沒有「被偷」過，但別人已經在拿它撞你的門。

### 防禦教訓

1. **別重用密碼**。用密碼管理器為每個網站產生獨一無二的密碼，是成本最低、效果最好的防禦（相關做法見 `pass-04-defenses`）。
2. **啟用 MFA（多因素驗證）**，就算密碼被撞破，第二道關卡仍能擋住。
3. 監控「帳號是否出現在外洩清單」的服務，及早發現、及早重置。
4. 對服務商來說，敏感資料的分享功能應改為「預設關閉、明確同意」。

## 把教訓變成行動：工程師的落地三步

#### 盤點目前的密碼存放方式

去資料庫看一張使用者表：欄位存的是明文、可逆加密，還是加鹽的慢速雜湊？這是第一張照妖鏡。

#### 升級到慢速加鹽雜湊

改用 bcrypt、argon2 或 scrypt。每個密碼產生獨一無二的鹽，並逐步遷移舊資料。\n\n→ 複習：crypto-02-password-hashing

#### 把 MFA 與外洩監控接上

讓就算密碼失守，帳號也還有第二道鎖；並用外洩監控服務，及早發現自家帳號被捲入別人的資料庫。

## 五個共通教訓

把四起案例放在一起，真正的重點其實重複了五次：

1. **密碼存放方式決定一切**——明文、無鹽快雜湊、可逆加密，三種做法三種災難。
2. **鹽要獨一無二**——每個密碼都該有屬於自己的鹽。
3. **雜湊要慢**——自適應演算法把暴力破解成本拉到天價。
4. **別重用密碼**——攻擊者最愛的不是破解，而是「拿舊密碼撞新門」。
5. **多一層驗證**——MFA 與監控，讓「密碼失守」不等於「帳號失守」。

## 一份可以照做的防禦檢查清單

| 檢查項 | 過關標準 |
|--------|---------|
| 密碼存放 | 只用 bcrypt / argon2 / scrypt，而且加了鹽 |
| 鹽 | 每個密碼獨立、隨機 |
| 明文與可逆加密 | 資料庫裡找不到任何能還原成密碼的欄位 |
| MFA | 重要帳號全部啟用 |
| 密碼重用 | 用密碼管理器，每個網站一個密碼 |
| 外洩監控 | 訂閱監控服務，發現即重置 |

> 如果只能帶走一句話：你的防禦不是看密碼「好不好記」，而是看它被偷走之後「值不值錢」。 雜湊＋鹽＋MFA，就是讓它不值錢的組合。

## 小測驗

#### Q: RockYou 事件最震撼的教訓是什麼？

* 用 SHA-1 儲存密碼就夠安全了

* 密碼以明文儲存，攻擊者連解碼都不用

* 只要設了密碼提示問題就安全

* 加了鹽的密碼永遠不會被破解

> 💡 RockYou 的約 3,200 萬筆密碼直接以明文存放在資料庫，攻擊者拿到資料庫就等於拿到全部密碼，連破解都不需要。
