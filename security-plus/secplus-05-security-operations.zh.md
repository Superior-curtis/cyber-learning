# 安全營運（監控、加固、應變）

> 📅 2026-08-05 · 核心概念
> 防禦不是「設好就忘」——安全是每天的例行工作。監控與告警、日誌、漏洞管理、修補、事件應變與數位鑑識，是安全團隊的日常戰線。

---

## 急診室與日常保養

如果 `secplus-04-security-architecture` 是房子的藍圖，那安全營運就是住進去之後的每一天：有人巡邏、有人檢查門窗、壞天氣來之前有人加固、真出事的時候有人處理。營運看起來沒有設計那麼「帥」，但歷史上的重大事件，多半不是敗在藍圖，而是敗在**日常沒人看顧**。

這一章的關鍵詞是「循環」：防護 → 偵測 → 應變 → 檢討 → 再防護。它不是一次性的專案，而是不會停的例行工作。下面把安全團隊的日常戰線，一條一條拆開。

## 監控與告警：在壞事之前先知道

監控的目的，是**在攻擊造成重大傷害之前先發現它**。做法是先知道「正常長什麼樣」，然後盯住「不正常」。

| 監控項目 | 看什麼 | 異常徵兆 |
|---------|--------|---------|
| 登入行為 | 誰、從哪、何時登入 | 凌晨三點的管理員登入、來自陌生國家的 IP |
| 帳號活動 | 權限變更、新帳號建立 | 突然有人把自己加進管理群組 |
| 網路流量 | 連線方向與流量大小 | 內部機器大量往外送資料（資料外洩徵兆） |
| 系統資源 | CPU、記憶體、程序 | 陌生程序吃掉大量資源（可能的挖礦或後門） |

告警的關鍵設計是**分級與去重**：把「需要人處理」和「只是參考」分開，別讓每一件小事都驚動值班人員。這裡有個真實的兩難——**誤報太多，人會開始忽略所有告警（告警疲勞）**；誤報太少，又怕漏掉真的攻擊。好的做法是慢慢調整閾值，讓告警數量降到「人真的會去看」的水準。

## 日誌：調查的底稿

告警告訴你「現在可能有狀況」，但回答「到底發生什麼」的，是**日誌**。日誌是整場事件的底稿：誰、在什麼時間、做了什麼。沒有日誌，你只能猜；有日誌，你才能重建時間線、找出受影響的範圍。

營運面有幾個關於日誌的基本原則：

* **記錄重要的事**：登入、權限變更、系統設定變更、管理員操作，比一般存取更有價值。
* **集中存放**：把各機器的日誌送到同一個地方（例如 SIEM），否則出事時要一台台翻。
* **時間同步**：所有機器對時（NTP），否則時間線對不起來。
* **保護完整性**：日誌要防竄改，攻擊者不該能「清洗」證據。

SIEM 會把日誌、監控與告警串成一個平台——`blue-02-logging-siem` 會把整套架構拆開講。這裡先記住主線：**沒有日誌，就沒有調查；沒有調查，就沒有學習。**

## 漏洞管理：知道風險在哪裡

**漏洞管理**是「有系統地找出系統裡的弱點，並排定修補優先序」的流程。它有四步：盤點資產 → 定期掃描 → 依風險排序 → 追蹤到修好為止。

掃描器（如 Nessus、OpenVAS）會把已知漏洞（`cve-01-what-is-cve`）與系統版本比對，找出「這台機器有哪些漏洞」。但掃描結果不是拿來照單全收的——幾百個漏洞列出來，真正緊急的往往只有幾個。排優先序要看的不是「漏洞多不多」，而是**「這個漏洞配上我的環境，風險多高？」**

| 風險考量 | 問題 |
|---------|------|
| 資產價值 | 被影響的是對外網站，還是內部測試機？ |
| 暴露程度 | 這台機器對網際網路開放嗎？還是深在內網？ |
| 有無已利用 | 野外是否已有攻擊程式在流傳？ |
| 有無修補 | 官方是否已釋出修補？還是需要替代控制？ |

> CVSS 分數只是起點，不是結論。 一顆 9.8 分的漏洞如果只影響一台不連外網的測試機，優先序不一定高於一顆 7 分、卻正被打在對外服務上的漏洞。漏洞管理的核心是「根據風險排程」，不是「按分數機械式照做」。

## 修補管理：把漏洞關起來

掃描發現漏洞之後，真正把它關掉的是**修補（patching）**——安裝廠商釋出的更新，讓漏洞不再存在。修補的流程是：測試 → 排程 → 部署 → 驗證。

| 階段 | 內容 |
|------|------|
| 評估 | 確認修補與自家環境相容，小範圍試裝 |
| 排程 | 挑影響最小的時間窗（通常是非尖峰時段） |
| 部署 | 分批推送，隨時可回滾 |
| 驗證 | 確認修補後系統正常、漏洞已消失 |

修補最大的敵人，是「這次維修會不會弄壞系統」與「不修補的漏洞會不會先被利用」之間的拉扯。企業會用**修補時限（patch SLA）**把這個拉扯制度化：例如高風險漏洞 72 小時內修補、中風險 30 天內。遇到**零時差漏洞（zero-day）**——廠商還沒有修補的漏洞——就只能先靠替代控制（防火牆規則、監控、暫時關閉服務）撐著。這部分的完整戰術在 `cve-06-patch-management`。

> 別只修補「你記得」的機器。 資產盤點沒做乾淨，就會出現一批「沒人記得它存在」的伺服器，它們恰恰是最容易被入侵的。修補管理的前一步，永遠是「我知道我有什麼」。

## 加固：把攻擊面縮小

**加固（hardening）**是「把不必要的部分拿掉，讓攻擊面變小」的總稱——修補只是其中一環。它的精神很簡單：**系統能不做的事，就不要讓它做；能不放開的地方，就不要放開**。一份典型的主機加固檢查清單長這樣：

* [ ] 移除或停用預設帳號、預設密碼與範例檔案
* [ ] 關閉用不到的服務、連接埠與排程工作
* [ ] 套用最新的安全修補與設定基準線
* [ ] 以最小權限建立帳號，管理任務改用專用帳號
* [ ] 開啟稽核與日誌，並集中存放
* [ ] 設定本機防火牆，只允許必要流量
* [ ] 停用不安全的協定與過時的加密演算法

加固要的是「維持」而非「一次性專案」：每一台機器上線時都從乾淨的基準線（`secplus-04-security-architecture` 提過的金映像）出發，並定期複查設定漂移。`blue-01-hardening` 有更完整的作業系統與服務加固細節——這裡只要記住，加固、修補與漏洞管理是一組互相咬合的工作。

## 事件應變：六個階段

防護再完整，總有一天會出事。**事件應變（incident response）**是「出事之後，用一套流程把傷害降到最低」的劇本。業界常用的 NIST 六階段是：

| 階段 | 在做什麼 |
|------|---------|
| 準備（Preparation） | 平時就備好流程、工具、聯絡人與授權 |
| 偵測與分析（Detection） | 發現徵兆、確認是否為真實事件、收集資訊 |
| 遏制（Containment） | 止血：隔離受影響系統，阻止擴散 |
| 根除（Eradication） | 移除入侵者的立足點、清除惡意檔案 |
| 復原（Recovery） | 把系統恢復到安全狀態、驗證正常 |
| 教訓（Lessons learned） | 檢討流程、回饋到下一次的準備 |

> 最關鍵的階段是「準備」，而它往往被跳過。 真正出事的當下，人處於慌亂與疲憊之中，不可能現場把流程想出來。事前寫好的應變手冊、備好的工具與聯絡清單，才是應變的基礎——這正是 blue-04-incident-response 要深入展開的內容。

應變的第一準則是**別急著把機器重灌**。在保存證據與恢復營運之間，需要走一套有紀律的流程——這就接到數位鑑識。

## 數位鑑識：出事之後怎麼取證

**數位鑑識（digital forensics）**是從數位證據中，還原「到底發生什麼」的學問。它不只是「看看檔案」，而是一套講究證據力的流程：

* **保全現場**：在證據被破壞前先保存，別急著動手清理。
* **製作映像（imaging）**：對磁碟做逐位元副本，之後只分析副本，不動原碟。
* **保存鏈（chain of custody）**：證據每一次轉手都要記錄，證明證據沒有被動手腳。
* **時間線重建**：把檔案、日誌、系統時間湊成事件順序。

鑑識的價值在於：它不只是抓證據，也回答「攻擊者怎麼進來、停留多久、帶走了什麼」——這些答案會回饋到下一次的防護與應變。更細的工具與手法，會在 `blue-05-forensics` 展開。

## 人員與流程：工具只是輔助

把前面幾節合起來看，安全營運的成功其實不太依賴「買了多貴的工具」，而依賴**流程有沒有被真的執行、人有沒有被訓練到位**。三個容易被忽略的環節：

* **Runbook（操作手冊）**：把例行工作寫成步驟，任何人接手都能照做。
* **桌上演練（tabletop exercise）**：用模擬事件演練應變流程，出事先練過就不慌。
* **輪值與交接**：監控是 24 小時的事，交接不清會讓事件被漏掉。

人會犯錯、會累、會忽略——所以營運系統的設計，要預設「操作者會犯錯」，用檢查清單、自動化與複核來兜底。

## 一句話總結

安全營運的全部，可以收進一個循環：**防護 → 偵測 → 應變 → 檢討**。監控與日誌負責「看到」，漏洞與修補負責「堵上」，事件應變與鑑識負責「處理乾淨」，最後把教訓送回起點。這個循環不會停——它靠的不是某個天才，而是流程、工具與被訓練過的人，日復一日地跑下去。

## 下一步

從監控、日誌、漏洞、修補到應變與鑑識，安全營運是一整條不會停的循環。但它們都建立在一個前提上：**有人拍板決定該做什麼、有資源、有規則**。下一章 `secplus-06-governance-risk` 會往上游看——風險管理、政策與合規，是讓這整條營運循環「運轉得下去」的制度基礎。

#### Q: 事件應變六階段裡，為什麼「準備」階段被認為最關鍵？

* 因為出事的當下人處於慌亂，事前備好的流程與工具才是應變的基礎

* 因為準備階段可以直接阻止攻擊發生

* 因為沒有準備階段，數位鑑識就無法進行

* 因為準備階段是最花錢的一個階段

> 💡 真正的事件當下，人無法臨場設計流程；事前準備好的手冊、工具與聯絡清單，決定應變能不能有效執行。其他選項不是準備階段的核心理由。
