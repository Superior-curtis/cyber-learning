# 注入：SQLi / XSS / 命令注入與防禦

> 📅 2026-08-05 · 深入研究
> 「把使用者輸入當成程式執行」——這是注入的本質，也是 OWASP A03。SQL 注入、XSS、命令注入各自怎麼發生、又有什麼共同的防禦原則？這篇一次講清楚。

---

在 `web-01-owasp-top10` 的十大清單裡，A03「注入」是被引用最多的名字之一。它是一個**大家族**——SQL 注入、XSS、命令注入都算。三者的共同本質只有一句話：

> **把使用者輸入，當成了程式碼來執行。**

這篇拆解三種最常見的注入，並把「共同的防禦原則」講透。記住原則，比背漏洞編號重要得多。

## 注入是什麼：把輸入當程式

正常情況下，程式把使用者輸入當成「資料」處理——存起來、比對一下。注入的問題發生在**資料與程式碼沒有分開**：當使用者輸入被直接拼進「會被執行的東西」裡，輸入就變成了程式的一部分。

舉例：一個查詢是「找出叫小明的人」，如果使用者能控制「名字」這個欄位，而程式把欄位直接拼進 SQL 查詢，使用者就可以輸入「小明 OR 1=1」，讓查詢變成「找出所有人」。

> 記憶這個心智模型：注入 = 資料與程式碼的界線被打破。 所有注入防禦，本質上都是在「重新建立這條界線」。

## SQL 注入

SQL 注入發生在**資料庫查詢**被拼裝的地方。經典防禦是**參數化查詢（prepared statement）**：

```
# 錯誤：把使用者輸入直接拼進字串
sql = "SELECT * FROM users WHERE name = '" + userInput + "'"

# 正確：參數化，輸入永遠是「資料」，不是「語法」
sql = "SELECT * FROM users WHERE name = ?"
```

差別就在：參數化之後，資料庫知道 `?` 這個位置只能是「值」，無論你輸入什麼，都不可能變成新的 SQL 語法。**這是 SQL 注入的標準解法，沒有之一。**

## XSS（跨站腳本）

XSS 發生在**網頁輸出**的地方：使用者輸入被原封不動地印回頁面，瀏覽器把它當成 HTML 或 JavaScript 執行。後果通常是「在別人的瀏覽器裡執行你的程式」——偷 Cookie、冒充身分。

兩道關鍵防禦：

* **輸出編碼（escaping）**：輸出的時候，把 `<`、`>`、引號等特殊字元轉義，讓瀏覽器把它當純文字，而不是標籤。
* **CSP（內容安全政策）**：告訴瀏覽器「這個頁面只允許執行自己網域的腳本」，即使有惡意腳本被注入，也會被擋下。

現代框架大多預設做輸出編碼，所以**不要手動關掉框架的這個安全行為**。

## 命令注入

命令注入發生在**呼叫作業系統指令**的地方：使用者輸入被拼進 shell 命令。例如一個「ping 一下這個地址」的功能，如果地址直接被拼進 `ping <地址>`，使用者輸入 `127.0.0.1; rm -rf /tmp/x`，就等於執行了兩條指令。

防禦原則非常明確：

* **能不呼叫 shell，就不要呼叫**——很多功能根本不需要開 shell。
* **非呼叫不可時，永遠用「參數陣列」傳遞**，而不是拼字串，並把可允許的字元白名單化。

> 這是防守課，不是攻擊課。 這裡只描述「注入是怎麼發生的」與「怎麼防」。對你自己的測試環境做注入練習時，請使用刻意脆弱的靶機（例如 lab-02-vulnerable-targets 提到的 DVWA），並保持在授權範圍內。

## 共同的防禦原則

把三種注入放在一起看，防禦其實是三句話：

1. **永遠不要把使用者輸入拼進「會被執行的東西」**——無論是 SQL、HTML 還是 shell。
2. **使用框架提供的安全機制**：參數化查詢、自動輸出編碼、限制 shell 用法。這些是被千錘百煉過的，不要自己發明。
3. **縱深防禦**：就算某一層失守，還有下一層——例如 CSP、資料庫帳號只給最小權限、伺服器不以 root 跑。

> 最高指導原則：預設「輸入不可信」。 任何來自使用者的資料，在系統邊界就當成「可能有問題」來處理。養成這個習慣，大部份注入漏洞在寫程式的當下就被防掉了。

#### Q: SQL 注入的標準防禦是什麼？

* 把所有使用者輸入轉成大寫

* 使用參數化查詢，讓輸入永遠是資料而不是語法

* 在資料庫前面加一個防火牆就夠了

* 把資料庫密碼設得長一點

> 💡 參數化查詢讓資料庫明確知道某個位置只能是值；無論輸入什麼，都不可能變成新的 SQL 語法。
