# 認證與 Session 安全

> 📅 2026-08-05 · 核心概念
> 網站怎麼知道「你是你」？密碼只是一半，Session 與 Cookie 是另一半。這篇拆解認證與 Session 的運作方式、常見攻擊，以及該怎麼設計才不會被偷走身分。

---

你登入一個網站，關掉分頁，隔天再開——它居然還記得你是誰。這不是魔法，而是 **Session（工作階段）** 的功勞。但如果 Session 被偷走，攻擊者就能「假裝是你」。

`web-01` 與 `web-02` 建立了地圖與注入防禦。這篇回答一個更貼身的問題：**網站怎麼確認身分，又怎麼確保這個身分不會被冒用？**

## 認證 vs 授權

先把兩個容易混在一起的概念分開：

* **認證（Authentication）**：你是誰？——登入、驗證身分。
* **授權（Authorization）**：你能做什麼？——驗證身分之後，決定你有沒有權限動某些東西。

就算認證完美，授權沒管好，還是會出事——這就是 OWASP A01「存取控制失效」。`web-01-owasp-top10` 的 A01 跟這裡是同一條線。

## 密碼只是一半

密碼是你「知道」的證明。但光靠密碼有個大問題：**如果密碼外洩（例如被釣魚或資料庫外洩），攻擊者就能直接登入。**

所以現代認證講究「多因素」——至少兩種不同類型的證明：

| 類型 | 例子 |
|---|---|
| 你知道的 | 密碼、PIN |
| 你擁有的 | 手機、安全金鑰、一次性驗證碼 |
| 你是的 | 指紋、臉部辨識 |

`pass-04-defenses` 已經把這套講得很透。這裡記住結論：**能加 MFA 就加，尤其是管理員帳號。**

## Session 與 Cookie：記憶你是誰

問題來了：HTTP 是「無狀態」的——伺服器不會自動記得上一次請求。要讓網站「記得你」，需要一個**識別身分的憑證**。

常見做法是：登入成功後，伺服器發一個 **Session ID**，放在 **Cookie** 裡。之後每次請求都帶著它，伺服器就知道「這是剛剛登入的那個人」。

```
# 概念示意：登入後伺服器發給瀏覽器的 Session Cookie
Set-Cookie: session=abc123; HttpOnly; Secure
```

關鍵在於：**這個小小的 ID 就是你身分的鑰匙。** 誰拿到它，誰就能冒充你。

> 把 Session ID 想成「飯店房卡」：登入就是發房卡，之後刷卡進門。房卡掉了，拿到的人就能進你的房間。所以房卡（Session）要難複製、要會過期、而且不能在容易被偷的地方傳遞。

## 常見攻擊

* **竊取 Session**：透過 XSS（`web-02-injection` 講過）偷走 Cookie，或在使用者手機上安裝惡意程式。拿到 Session 就等於拿到身分。
* **暴力破解密碼**：攻擊者嘗試大量常用密碼。防禦靠「嘗試次數限制」與 MFA。
* **重放**：攔截別人的請求，稍後原封不動重送。防禦靠時間戳、隨機數與 HTTPS。
* **會話固定**：攻擊者先取得一個 Session ID，再誘騙使用者用它登入，之後共用身分。防禦靠「登入後換新的 Session ID」。

## 安全設計原則

把上面的風險轉成一份簡短的設計清單：

| 原則 | 做法 |
|---|---|
| Cookie 加 HttpOnly | JavaScript 讀不到，降低被 XSS 偷走的機率 |
| Cookie 加 Secure | 只透過 HTTPS 傳送 |
| Session 逾時 | 一段時間沒動作就自動登出 |
| 登入後輪換 Session ID | 防會話固定 |
| 嘗試次數限制 + MFA | 防暴力破解 |
| 全程 HTTPS | 防攔截與重放 |

> 一個最常見的錯誤：用「把使用者的身分放進 Cookie 讓使用者自己保管」。 例如把使用者名稱或權限等級直接寫在 Cookie 裡——那等於把鑰匙交給使用者自己改。永遠用伺服器端管理的 Session，而不是客戶端可篡改的資料。

#### Q: 為什麼不應該把「使用者身分」直接放在可被使用者修改的 Cookie 裡？

* 因為 Cookie 只能存很短的內容

* 因為那等於把鑰匙交給使用者自己改，身分可以被竄改

* 因為瀏覽器不支援 Cookie

* 因為 Cookie 無法加密

> 💡 身分應該由伺服器端管理；把使用者名稱或權限直接放進可被修改的 Cookie，等於讓使用者自己決定自己是誰。
