# SSRF、CSRF 與檔案上傳

> 📅 2026-08-05 · 深入研究
> 三個常被低估的風險：讓伺服器替你訪問內部資源（SSRF）、從你的瀏覽器偷偷發出請求（CSRF）、上傳一個意料之外的檔案。這篇拆解它們怎麼發生，以及該怎麼防。

---

`web-01` 到 `web-03` 已經建立起網頁安全的地圖、注入與身分。這篇收尾三類常被低估的風險：**SSRF、CSRF、檔案上傳**。它們不像 SQL 注入那麼有名，但造成的破壞一點都不小。

## SSRF：讓伺服器替你打內網

SSRF（Server-Side Request Forgery，伺服器端請求偽造）發生在**伺服器會根據使用者提供的網址去抓取資源**的地方——例如「輸入圖片網址，幫你抓回來」。

問題在哪？伺服器通常位在內網，能訪問**只有內網才能訪問的服務**。如果使用者可以控制「抓取的目標」，就能讓伺服器去訪問那些不該對外的東西：內網的管理介面、雲端的 metadata 服務、本機的服務。

防禦重點：

* **白名單**：只允許抓取你預期的主機或網域，而不是任何網址。
* **阻擋內部位址**：拒絕 `127.0.0.1`、私有 IP、雲端 metadata 位址。
* **最少權限**：就算被抓取，能訪問的服務也越少越好。

> 把 SSRF 想成「讓一個住在公司裡的員工替你跑腿」——他擁有你沒有的內部權限，所以你要非常小心他跑去哪裡。

## CSRF：從你的瀏覽器偷發請求

CSRF（Cross-Site Request Forgery，跨站請求偽造）是反過來的問題。攻擊者**不偷你的身分**，而是利用「你已經登入」這件事：惡意網站悄悄讓你的瀏覽器對你登入過的網站發送一個請求。

因為瀏覽器會自動帶上你的 Session Cookie，伺服器就會以為「這是本人操作」——於是「改密碼」「轉帳」這類動作就被偷偷執行了。

標準防禦是 **CSRF Token**：伺服器在每個表單裡放一個只有本人頁面才有的隨機 Token，收到請求時驗證它。攻擊者的網站拿不到這個 Token，請求就會被拒。

```
# 概念：表單裡帶一個伺服器才知道的隨機 Token
<input type="hidden" name="csrf_token" value="隨機亂數">
```

> 記住這個區別：XSS 偷你的身分，CSRF 借你的身分。 所以 CSRF 的防禦是「驗證請求真的來自你自己的頁面」，而現代框架大多內建了這層保護——別關掉它。

## 檔案上傳：意料之外的檔案

網站允許上傳檔案很常見——頭像、附件、匯入資料。風險在於：**上傳的檔案如果被伺服器「執行」而不是「存放」，就可能變成攻擊面。**

典型問題：

* 上傳一個「看似圖片，其實是程式」的檔案，伺服器把它當程式執行。
* 檔案沒有驗證類型與大小，佔滿磁碟或消耗資源。
* 上傳的檔案被其他使用者下載時，內容被當成 HTML/腳本執行（例如 `.svg` 裡藏 XSS）。

防禦重點：

* **驗證類型**：用「內容本身」判斷類型，而不是相信副檔名或 `Content-Type`。
* **存到外部位置或專用目錄**，並以隨機檔名存放，避免「路徑＝可預測的執行檔」。
* **下載時當附件處理**：設定正確的 `Content-Disposition`，避免瀏覽器把檔案當成頁面執行。

## 三者的共同心法

SSRF、CSRF、檔案上傳，其實指向同一件事：**「輸入」與「請求」都不可信任，都要在系統邊界驗證。**

| 風險 | 一句話防禦 |
|---|---|
| SSRF | 伺服器抓取只允許白名單目標 |
| CSRF | 表單帶隨機 Token，驗證請求來源 |
| 檔案上傳 | 驗內容、存外圍、當附件下載 |

#### Q: CSRF 的攻擊者利用的是什麼？

* 偷走使用者的密碼

* 使用者已經登入的狀態，誘使瀏覽器帶著身分發出請求

* 直接在伺服器上執行任意程式

* 竄改使用者的 Session Cookie

> 💡 CSRF 不偷身分，而是借身分：惡意網頁讓已登入的瀏覽器對目標網站發送請求，伺服器誤以為是本人操作。
