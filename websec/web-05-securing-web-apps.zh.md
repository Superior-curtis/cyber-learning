# 打造安全的 Web App / API

> 📅 2026-08-05 · 使用教學
> 前面五篇拆開了各種風險，這篇把它們組裝起來。安全不是上線前的最後一步，而是從威脅模型開始、貫穿開發的一種做法。這篇給你一套可以直接上手的流程。

---

從 `web-01` 到 `web-04`，你已經認識了地圖、注入、身分、SSRF/CSRF/上傳。但你會發現一個問題：**知道了所有風險，不代表知道從哪裡開始做。** 這篇把積木組裝起來，給你一套「從頭安全」的做法。

## 安全不是最後一步

最常見的錯誤是：開發完，上線前，才「加安全」。但到那時候，很多問題已經長在架構裡，改起來又貴又痛。

更好的做法是**把安全當成設計的一部分**，貫穿整個流程。好消息是：這不需要你很「懂攻擊」，只需要一套有紀律的流程。

## 從威脅模型開始

動手寫程式之前，先問四個問題——這正是 `found-04-threat-modeling` 的心法：

1. **我們保護什麼？** 使用者的密碼？付款資料？商業機密？
2. **誰想拿它？** 隨機路過的攻擊者，還是有針對性的威脅？
3. **從哪進來？** 登入表單？API？檔案上傳？
4. **被打穿會怎樣？** 影響有多大，值不值得花多少力氣防？

答案會告訴你優先順序：一個儲存信用卡的網站，與一個只放公開文章的部落格，防禦力道完全不同。

## 核心防禦清單

把前面文章的結論收成一份「每個 Web App 都該有」的清單：

| 層 | 一定要有 |
|---|---|
| 傳輸 | 全站 HTTPS（`net-02-tls-https`） |
| 資料庫 | 參數化查詢（`web-02-injection`） |
| 輸出 | 框架的輸出編碼 + CSP（`web-02-injection`） |
| 身分 | 強密碼、MFA、伺服器端 Session、嘗試限制（`web-03-auth-session`） |
| 密碼儲存 | argon2/bcrypt（`crypto-02-password-hashing`） |
| 請求 | CSRF Token、SSRF 白名單（`web-04`） |
| 檔案 | 驗內容、存外圍（`web-04`） |
| 權限 | 最小權限，預設拒絕（`secplus-02-general-concepts`） |

> 這份清單不是「做完就安全」的保險，而是「地基」。 它確保最普遍的問題不出現；接著你仍需要持續測試，來發現清單之外的問題。

## API 特有的考量

如果你的服務是 API（例如手機 App 的後端），還有幾件事要特別注意：

* **認證**：用標準的 Token 機制，而不是自製的「夾帶身分」方案；`web-03-auth-session` 的警告在這裡同樣適用。
* **限流（rate limiting）**：限制單一使用者在一段時間內的請求次數，防暴力破解與濫用。
* **輸入驗證**：每個進入點都驗證——欄位型別、長度、範圍。永遠預設輸入不可信。
* **不要暴露過多資訊**：錯誤訊息不要洩漏堆疊或內部結構，`blue-02-logging-siem` 會談怎麼記錄而不洩密。

## 持續測試

「寫完再檢查一次」也不夠。安全需要**持續**：

* **依賴更新**：定期更新套件，追蹤已知漏洞——這正是 `cve-06-patch-management` 的主題。
* **自動化掃描**：把掃描工具接進 CI，每次變更都跑。
* **授權的滲透測試**：定期請（或自己做）有授權的測試，模擬攻擊者視角——`kali-04-burp-suite` 到 `kali-*` 一系列就是做這件事的工具。
* **紀錄與監控**：出了事要能被發現，`blue-02-logging-siem` 講的就是這塊。

## 下一步

Web 安全的地圖到此完整。接下來把知識變成手感：`kali-01-what-is-kali` 帶你認識資安人的瑞士刀——Kali Linux，以及怎麼用裡面的工具（例如 Burp Suite）對自己授權的系統做真實的測試。

#### Q: 把安全做進開發流程的第一步是什麼？

* 先寫好防火牆規則

* 先做威脅模型：保護什麼、誰想拿、從哪進來、被打穿會怎樣

* 先把所有套件更新到最新

* 先安裝防毒軟體

> 💡 威脅模型決定優先順序：不同系統要保護的東西不同，防禦力道也不同。先想清楚要保護什麼，才知道該花多少力氣。
