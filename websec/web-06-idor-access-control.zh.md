# IDOR 與存取控制

> 📅 2026-08-05 · 深入研究
> 「把網址裡的 id 改一個數字，就看到別人的資料」——這就是 IDOR，存取控制失效最常見的形式。這篇拆解它是怎麼發生的、為什麼「靠隱藏」不夠，以及唯一的防禦。

---

`web-01-owasp-top10` 的榜首是 A01「存取控制失效」。而它最常見、也最好懂的形式，就是 **IDOR**——把網址或請求裡的某個 id 改一下，就看到了不該看的資料。

這篇把它講透：怎麼發生、為什麼「以為沒人知道」不算防禦、以及真正有效的防禦是什麼。

## 什麼是 IDOR

**IDOR（Insecure Direct Object Reference，不安全的直接物件引用）** 是這樣發生的：程式直接用**使用者提供的 id** 去存取資料，卻**沒有檢查「這個使用者有沒有權限看這筆資料」**。

```
# 概念示意：直接拿 id 查詢，沒檢查權限
GET /orders?id=123    → 200 {"order":"我的訂單"}
GET /orders?id=124    → 200 {"order":"別人的訂單"}   # 問題出在這裡
```

只要資料庫裡有 id=124，而程式不檢查「124 是不是你的」，你就看到了別人的訂單、檔案、訊息。**問題不在於「猜不猜得到 id」，而在於「伺服器根本沒有做授權檢查」。**

## 為什麼「靠隱藏」不夠

這是最常被誤解的點。很多人以為「id 那麼長、那麼隨機，別人猜不到就安全」。**這是錯的**，原因有三：

1. **id 常常可以被列舉**：`?id=123` 試 `124`、`125`，一小段時間就掃完了。
2. **id 會從別處洩漏**：歷史訊息、分享連結、社群截圖，都可能把別人的 id 帶出來。
3. **安全不能建立在「祕密」上**：`web-05-securing-web-apps` 講過，正確的心態是「輸入不可信」。

**安全 = 伺服器端驗證授權。** 使用者提供 id 只是「想訪問這筆資料」，允許不允許，必須由伺服器用「登入者是誰 + 他對這筆資料有沒有權限」來決定。

## 存取控制失效的家族

IDOR 只是 A01 的一種。整個家族都指向同一件事：**權限沒檢查。**

| 形式 | 一句話 |
|---|---|
| IDOR | 直接改物件 id |
| 權限提升 | 普通帳號做管理員動作 |
| 方法越權 | 該用 GET 的用 POST 就繞過限制 |
| 垂直/水平越權 | 跨角色 / 跨使用者存取 |

> 記憶這個判準：任何「用使用者提供的標識符直接存取資源」的程式，都必須先問「這個使用者對這個資源有權限嗎」。 少了這一步，就是 A01。

## 防禦

防禦不是「把 id 藏起來」，而是**在伺服器端建立授權檢查**：

1. **每個資源存取都驗證權限**：查詢時，把「當前使用者」與「資源的擁有者/授權者」綁在一起比對。
2. **用「不透明」的引用**：能用資料庫內部隨機 ID，就不暴露可列舉的順序號。
3. **預設拒絕**：`blue-01-hardening` 的預設拒絕原則——沒明確允許，就不放行。
4. **測試時主動驗證**：把自己登入成「使用者 A」，試著訪問「使用者 B」的資源——這是測試清單上必測的一項。

## 下一步

IDOR 是「伺服器沒檢查權限」。下一類漏洞更「難搞」：`web-07-business-logic` 帶你認識業務邏輯漏洞——程式「照規則跑」，但規則本身可以被繞過或濫用。
