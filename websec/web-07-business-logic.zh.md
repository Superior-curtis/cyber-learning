# 業務邏輯漏洞

> 📅 2026-08-05 · 深入研究
> 程式照規則跑，但規則本身可以被繞過或濫用——這就是業務邏輯漏洞。它沒有固定簽名、掃描器抓不到，卻常常直接造成金錢或流程損失。這篇用例子拆開它，並給你防禦方向。

---

前幾篇的漏洞（注入、IDOR）都有「明確的壞輸入」。但有一類漏洞，**輸入看起來完全正常，程式也照規則跑——只是規則本身可以被濫用**。這就是 **業務邏輯漏洞（business logic flaw）**。

它特別難搞：沒有固定簽名、自動掃描器幾乎抓不到，卻常常直接造成金錢或流程上的損失。

## 什麼是業務邏輯漏洞

業務邏輯是「這套系統本來該怎麼運作」的規則：折扣怎麼算、限購怎麼限制、流程分幾步。漏洞發生在**規則可以被繞過或濫用**，而程式沒有發現。

跟技術漏洞的區別：

| | 技術漏洞（如注入） | 業務邏輯漏洞 |
|---|---|---|
| 輸入 | 明顯異常 | 看起來完全正常 |
| 掃描器 | 可能抓到 | 幾乎抓不到 |
| 根因 | 程式沒驗證輸入 | 規則本身有漏洞 |
| 後果 | 資料/系統被突破 | 金錢/流程被濫用 |

## 幾個經典例子

* **折扣濫用**：把「折扣碼可重複使用」的規則重複套用到極限——每個輸入都合法，但結果違背了「一人一次」的意圖。
* **數量為負**：購物車數量設成 `-1`，總價反而變負——程式沒檢查數量下限。
* **流程跳過**：結帳分「選商品 → 付款 → 出貨」三步，但直接呼叫「出貨」步驟就跳過了付款。
* **競態**：同一張優惠券同時用兩次，兩邊都「檢查過」而都通過——`web-04-ssrf-csrf-upload` 提過的窗口問題。

> 共同的根源：程式檢查了「技術上對不對」，卻沒檢查「業務上合不合理」。 每個欄位都合法，但組合起來違反了業務規則。

## 為什麼掃描器抓不到

自動掃描器靠「壞輸入的簽名」來找漏洞——惡意的 SQL、異常的長度。但業務邏輯漏洞的輸入**完全正常**，它壞在「意圖」與「規則」：

* 掃描器不知道「一人只能用一次折扣碼」是規則。
* 掃描器不知道「數量不能為負」是規則。
* 這些規則只存在於**業務知識**裡。

所以它需要**人**：懂業務的人，在測試時想「如果我把這個流程這樣走，會怎樣？」

## 防禦方向

業務邏輯漏洞沒有單一補丁，但有幾條通用的防禦方向：

1. **在伺服器端強制業務規則**：折扣次數、數量範圍、狀態流轉——不能只靠前端（前端可被繞過）。
2. **流程有狀態**：結帳的每一步都要驗證「前一步真的完成了」。
3. **非單調操作加防重**：用冪等鍵（idempotency key）避免同一操作重複生效。
4. **測試時有人「邪惡地走流程」**：讓懂業務的人，像攻擊者一樣把正常流程反著走、跳著走、重複走。

> 提醒：這不是教你「怎麼製造虧損」，而是告訴防守方「該在哪裡檢查」。 對自己的系統，用「邪惡地走一遍正常流程」的心態去測，是找到這類問題最有效的方法。

#### Q: 為什麼業務邏輯漏洞幾乎抓不到自動掃描器？

* 因為它會讓掃描器當機

* 因為它的輸入完全正常，壞的是『意圖與規則』，而規則只存在於業務知識裡

* 因為它只影響付費功能

* 因為掃描器沒有足夠記憶體

> 💡 業務邏輯漏洞的輸入合法、沒有簽名；掃描器不懂『一人只能用一次』這類業務規則，所以必須靠懂業務的人測試。
