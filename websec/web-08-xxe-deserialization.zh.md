# XXE 與不安全的反序列化

> 📅 2026-08-05 · 深入研究
> 兩個『解析了不該解析的東西』的經典漏洞：XXE 讓 XML 解析器讀取本機檔案，不安全的反序列化把不可信資料變成物件。這篇用概念拆開它們，並給出防禦方向。

---

業務邏輯漏洞靠「人」找；而接下來這兩類，是「機器」該防的技術漏洞：**XXE** 與**不安全的反序列化**。它們的共同點是一句話：**解析了不該解析的東西。**

## XXE：XML 解析器的越權

**XXE（XML External Entity，XML 外部實體）** 發生在程式解析**使用者提供的 XML** 時，允許了「外部實體」。XML 的這個特性，可以讓解析器**幫你讀取本機檔案或發起請求**：

```
<!-- 概念示意：讓解析器去讀本機檔案 -->
<!DOCTYPE x [ <!ENTITY f SYSTEM "file:///etc/passwd"> ]>
<x>&f;</x>
```

如果解析器照做，`&f;` 就會展開成檔案內容——攻擊者等於**借用了伺服器的讀檔權限**。這本質上是一種類型的 **SSRF**（`web-04-ssrf-csrf-upload`）：讓伺服器替你訪問它才有權限的東西。

防禦方向很明確：

* **停用外部實體**：在 XML 解析器上關閉 DTD / 外部實體解析。
* **盡量不要解析不可信的 XML**：能改用 JSON 就改用 JSON。
* **最小權限**：就算解析，伺服器帳號也不該能讀敏感檔案。

## 不安全的反序列化：把資料變成物件

**序列化（serialization）** 是把物件變成可以傳輸/儲存的資料；**反序列化**是反過來，把資料變回物件。問題出在：**如果把「不可信的資料」交給反序列化，它可能被設計成「執行程式碼」或「建立奇怪的物件」。**

```
# 概念示意：從不可信來源反序列化
obj = unserialize(untrustedInput)   # 輸入可能被設計成載入任意類別
```

不同語言嚴重度不同，但核心風險一樣：**反序列化器會執行「資料裡描述的動作」**——而資料是你控制的。這就像把一段「程式」當成「資料」來處理，正是 `web-02-injection` 那句「把輸入當程式」的變體。

防禦方向：

* **絕不反序列化不可信的輸入**。
* 非用不可時，用**白名單**限制可被載入的類型。
* 用更安全的格式（如 JSON + 明確驗證）取代原生物件反序列化。

> 這兩個都是「防守課」——只描述漏洞與防禦，不提供可利用的負載。 理解「哪裡會被解析」是防守的第一步；把利用方法用在真實系統上就是攻擊。

## 共同的心法

把 XXE 與反序列化放在一起，會看到一條共同線：**「輸入會被解析/執行」的地方，就是攻擊面。**

| 漏洞 | 「被解析的東西」 | 防禦口訣 |
|---|---|---|
| XXE | 使用者提供的 XML | 關外部實體、別解析不可信 XML |
| 反序列化 | 不可信的序列化資料 | 別反序列化不可信輸入、白名單類型 |

而 `web-05-securing-web-apps` 那條最高原則在這裡再次成立：**預設輸入不可信。** 任何「會吃進資料並轉成結構/物件」的函式，都先問「這個輸入可以信嗎」。

#### Q: XXE 與不安全的反序列化的共同根源是什麼？

* 密碼太弱

* 程式解析了不該解析的輸入——XML 外部實體或不可信的序列化資料

* 防火牆設定錯誤

* 缺少備份

> 💡 兩者都是「解析/執行不可信輸入」：XXE 讓解析器讀檔，反序列化把資料變成物件；預設不信任輸入是共同防禦。
