# OAuth 範圍濫用：相簿盜取的案例拆解

> 📅 2026-08-05 · 深入研究
> 一個網站說『請授權上傳照片』，你按下同意，它卻把整本相簿搬走——這是 OAuth 範圍（scope）濫用的典型。這篇用它當案例，拆解第三方授權的機制、同意畫面與防禦。

---

**案例**：一個網站說「請上傳照片到你的相簿」，跳出授權頁面，你按下同意。之後——它開始把整本相簿、包括過去與未來的照片，大量搬走。

這不是科幻，而是真實存在的攻擊模式。它的名字叫 **OAuth 範圍濫用（scope abuse）**，而它同時也是一個**社會工程**案例。這篇用它當教材，一次講透。

## 這算什麼攻擊：三層拆解

把這個例子拆開，它其實是三件事疊在一起：

| 層 | 屬於 | 利用的是 |
|---|---|---|
| 誘餌 | 社會工程 | 「合理的名目」讓你願意按下同意 |
| 授權範圍 | OAuth / 授權濫用 | 你同意的權限遠超過實際需要 |
| 大規模搬運 | 資料外洩 | 拿到權限後，不是一張，是全部 |

> 一句話分類：它以社會工程當入口，以 OAuth 範圍濫用當手段，以大規模資料外洩當結果。 三層都要懂，才能完整防住。

## OAuth 與 scope：第三方授權的機制

網站為什麼能「用你的帳號做事情」？靠的是 **OAuth**——第三方授權機制。它讓一個網站「以你的身分」存取你在另一個平台的資料，**但只限你授權的範圍（scope）**。

關鍵在 scope：正常授權是「最小、具體」——例如 `上傳一張照片`。攻擊性授權是「過寬、含糊」——例如 `讀取並管理完整相簿`。

**OAuth 本身不是壞東西；壞的是「請求過寬的 scope + 使用者沒讀同意畫面」。**

## 同意畫面：決定一切的那一頁

當網站要求授權時，平台會顯示**同意畫面（consent screen）**——列出「這個網站將能存取哪些資料」。

```
# 概念：兩種同意畫面的對比
正常：這個網站將能 → 上傳照片（僅此一次）
濫用：這個網站將能 → 讀取你全部的相簿、新增內容、管理相簿
```

**攻擊者賭的就是：你不會讀這頁，直接按「同意」。** 名目（「上傳照片」）聽起來合理，實際勾選的權限卻過寬——而這正是 `pass-04-defenses` 講「最小權限」沒被應用到自己資料上的結果。

## 案例拆解：一步步

#### 誘餌

網站用「上傳照片」這類合理名目，讓你願意授權。

#### 過寬的 scope

同意畫面列出的是「完整相簿存取」，遠超過上傳需要——但多數人不會讀。

#### 你按下同意

授權建立，網站拿到了通往整個相簿的鑰匙。

#### 大規模搬運

網站開始把全部照片搬走——一張變一本，一次授權全洩。

> 安全說明：這是概念與防禦課。真實的 OAuth 授權是你自己的選擇——學會「讀同意畫面、檢查 scope」，而不是把案例變成任何人可照做的劇本。任何未經授權的資料取得都是犯罪。

## 為什麼有效：心理

* **合理名目**：標題說「上傳照片」，你預設它只做這件事。
* **順手同意**：多數人不讀授權細節，就像 `kali-16-camphish` 的「順手輸入」。
* **最小權限沒被應用**：你沒想過「它可以只給一張照片的權限」。

**防禦的心理根基，就是「把同意畫面當契約來讀」**——這比任何技術手段都有效。

## 防禦

| 角色 | 做法 |
|---|---|
| 使用者 | 讀同意畫面、只授權最小 scope、定期撤銷不用的應用授權 |
| 開發者 | 只請求真正需要的 scope、把名目講清楚 |
| 平台 | 顯示清楚的權限清單、限制過寬授權、提供授權管理頁 |

> 記住對照：攻擊者是「讓可理解的授權名目」配上「過寬的實際權限」；防禦就是「先讀，再最小化授權」。 這正是 web-03-auth-session 的授權精神，套用在「第三方應用」這一層。

#### Q: 『相簿盜取』案例的關鍵漏洞在哪裡？

* 平台伺服器被破解

* 網站請求了過寬的授權範圍，且使用者沒讀同意畫面就按下同意

* 照片檔案沒加密

* 作業系統有漏洞

> 💡 漏洞在『授權』這層：過寬的 scope + 不讀同意畫面 = 一次同意就把整本相簿交出去；防禦就是讀畫面、最小授權。
